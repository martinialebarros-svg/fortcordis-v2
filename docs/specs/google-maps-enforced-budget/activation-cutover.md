# Transição futura para orçamento monitorado

**Somente após revisão dos valores e autorização separada de produção.** Este roteiro não foi executado nesta preparação. Manter a liberação temporária até uma transição completa; salvar uma configuração enquanto a emergência segue ativa não passa a contabilizar as chamadas desse intervalo no ledger.

1. Revalidar o snapshot aprovado, o projeto/banco correto, `APP_ENV=production`, segredo forte, preços/validade, orçamento `monitor` e os limites escolhidos. Não promover incidentalmente alterações de autenticação ou laudos que ainda não estejam instaladas/autorizadas. Os patches de revisão não devem ser aplicados cegamente ao `main` divergente.
2. Instalar o código com emergência ainda true e preservar os dados de runtime. Preparar o payload e a revisão esperada, sem presumir consumo inicial zero ou saldo gratuito.
3. Na janela de transição autorizada, drenar e parar **todos** os processos capazes de enviar Google, incluindo API e worker. Comprovar encerramento das instâncias antigas e das chamadas em trânsito antes de fechar a coleta. O frontend pode preservar os formulários, mas haverá a breve indisponibilidade normal de API da manutenção; não prometer uma troca sem interrupção.
4. Com os emissores parados, fechar e registrar o baseline do dia/mês. Conciliar Billing por SKU/fuso com telemetria e logs de tentativas da liberação; não somar fontes sobrepostas como consumo real. Franquia da conta e dados atrasados não concedem crédito. Se não for possível verificar um limite superior confiável para os extras, **manter todas as ações não Agenda com `action_call_caps=0` e automações desabilitadas**, inclusive consultas avulsas/cadastrais. Só revisar essa suspensão após apuração; não chamar uma contagem incompleta de saldo disponível. A política da Agenda continua sendo a exceção explicitamente escolhida pelo usuário, com máximo finito por confirmação e alertas.
5. No processo administrativo controlado, sem provedores ou workers, configurar `GOOGLE_MAPS_COST_EMERGENCY_RELEASE=false`, `GOOGLE_MAPS_AGENDA_CACHE_FIRST=true` e salvar o orçamento monitorado com baseline, data/base da apuração e revisão esperada. A gravação passa pelo mesmo serviço transacional de configuração; não editar tabelas para contornar validações. Conferir por conexão independente os valores persistidos, a revisão, o modo monitorado e o histórico preservado.
6. Iniciar API e worker no snapshot verificado. Conferir situação efetiva, revisão do orçamento, `agenda_budget_mode=monitor`, cache-first e emergência false. Só então concluir a transição. Toda tentativa nova deve estar sob reserva durável; não pode existir uma instância antiga ainda liberada após o instante do baseline.
7. Executar smoke seguro da recepção, sem criar dados reais ou enviar Google para provar o bloqueio. Conferir que cache e validação normal funcionam, e que extras suspensos não enviam chamadas. A demonstração paga real, se necessária, exige consentimento próprio limitado e não faz parte deste roteiro de leitura.

Em incidente operacional, reabilitar a flag de emergência, reiniciar/verificar API e worker e comprovar o fluxo de recepção. Isso volta a permitir cobrança sem teto, preserva o ledger e exige nova conciliação antes de outra transição. Não realizar rollback somente do código com uma configuração nova incompatível; a política efetiva deve ser comprovada junto dos processos.
